# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Rally OpenStack Monitor — a containerized tool that runs OpenStack cloud tests via Rally on a cron schedule, exposes results as Prometheus metrics, detects orphaned resources from failed cleanups, and serves a read-only dark-theme dashboard.

## Commands

### Build and Run

```bash
# Pull the CI-published image and start the container (default)
cd docker && docker compose pull && docker compose up -d

# Or build locally instead of pulling (tagged with the same image name)
cd docker && docker compose up -d --build

# Trigger a manual test run inside the running container
docker exec -u rally rally-monitor /scripts/run_tests.sh

# Run a lightweight health check (non-destructive read-only API calls)
docker exec -u rally rally-monitor /scripts/health_check.sh

# Run cleanup orphan detection manually
docker exec -u rally rally-monitor /scripts/cleanup_monitor.sh

# Purge orphaned Rally resources (dry-run — shows what would be deleted)
docker exec -u rally rally-monitor /scripts/purge_orphans.sh

# Purge orphaned Rally resources (actually deletes them)
docker exec -u rally rally-monitor /scripts/purge_orphans.sh --confirm

# View live logs
docker logs -f rally-monitor
docker exec rally-monitor tail -f /rally/logs/rally-tests.log
docker exec rally-monitor tail -f /rally/logs/health-check.log
```

### Exporter (local dev, outside Docker)

```bash
cd exporter
pip install -r requirements.txt
RESULTS_DIR=./results python rally_exporter.py
```

### Setup

```bash
cp env.sample .env
# Fill in OS_AUTH_URL, OS_USERNAME, OS_PASSWORD, OS_PROJECT_NAME
```

## Architecture

The entire system runs in a single Docker container (`rally-monitor`) with three concurrent processes managed by `scripts/entrypoint.sh`:

1. **Prometheus Exporter** (`exporter/rally_exporter.py`, with the API-health gauges in `exporter/health_metrics.py`, the announcement gauges in `exporter/announcement_metrics.py`, and the shared registry/cron-spacing/ISO-parsing helpers in `exporter/metrics_common.py`) — Flask app on `:9101` that reads JSON files from `/results/` (`latest_summary.json`, `cleanup_metrics.json`, `health.json`, `announcement-state.json`) and exposes them as Prometheus gauge metrics on `/metrics`. Also serves `/health` (liveness) and `/ready` (readiness).

2. **Dashboard** (`dashboard/`) — Static files served by Python's `ThreadingHTTPServer` on `:8080`. The dashboard is pure HTML/CSS plus ES modules under `dashboard/js/` (see Dashboard Modules) with no build step; it fetches JSON by **relative** path (so it works behind a sub-path reverse proxy) from symlinked files (`results.json`, `history.json`, `health.json`, `health_history.json`, `announcement-state.json`, `run_state.json`) in the same directory, plus self-contained per-run HTML reports (rendered by `render_report.py`, see Full Report) via the `runs/` symlink.

3. **Cron Jobs** — `cron -f` runs as a supervised child of `entrypoint.sh` (in its `wait -n` set, so a dead cron exits the container). Two cron schedules:
   - Rally test runs (`RALLY_SCHEDULE_INTERVAL`, default 240 min) → `scripts/run_tests.sh`
   - API health checks (`HEALTH_CHECK_INTERVAL`, default 15 min) → `scripts/health_check.sh`

### File Layout (runtime volumes)

- `/results/` — Docker volume `rally-results`; persists across restarts
  - `latest_summary.json` — current run summary (seed file created on first boot)
  - `cleanup_metrics.json` — orphaned resource counts from `cleanup_monitor.sh`, plus `openstack_scan_status`/`openstack_scan_errors` (a failed list call is a scan error, never "0 orphans") and the `rgw_*` scan fields
  - `rally_project_ids.log` — append-only ledger of Rally-created Keystone project IDs for RGW purge provenance
  - `smoke_history.json` — rolling per-run `{timestamp, status}` uptime ledger with embedded uptime figures; pruned by `UPTIME_WINDOW_DAYS`, independent of run-directory retention
  - `results.json` — combined summary + cleanup + smoke uptime for dashboard
  - `history.json` — all retained per-run summaries for the timeline (compact JSON, `jq -c`, like `smoke_history.json` and `health_history.json`)
  - `health.json` / `health_history.json` — API health check results
  - `dashboard_config.json` — `{schedule_interval_seconds, health_check_interval_seconds, health_stale_after_seconds}`, rewritten on every boot by `init_state.sh` (as rally) from the normalized env, so a config change takes effect on restart; symlinked into the dashboard
  - `run_state.json` — `{state: running|idle, started_at, ...}` written by `run_tests.sh` (running after the run flock is held, idle via an EXIT trap incl. failure paths); reset to idle on every boot by `init_state.sh` (run as rally from `entrypoint.sh`)
  - `.last_notified_status` — `notify.sh` baseline (`passed`/`failed`); updated atomically only after a successful webhook send. Not symlinked into the dashboard (internal state)
  - `announcement-state.json` — operator announcement records (see Announcement System)
  - `<TIMESTAMP>/` — per-run directories with `<service>.json`, `<service>.html`, `run.log`
- `/rally/data/` — Docker volume `rally-data`; SQLite DB for Rally state
- `/dashboard/` — ephemeral; `results.json` etc. are symlinks → `/results/`; `/dashboard/runs -> /results` exposes per-run `<TIMESTAMP>/<service>.html` reports

### Dashboard Modules

`dashboard/index.html` loads the vendored Chart.js as a classic script (a global `Chart`) and then one `<script type="module" src="js/main.js">`; module scripts run under `script-src 'self'` with no build step. Modules under `dashboard/js/`, none of which touches the DOM at import time except the entry point:

- `main.js` — entry: refresh loop (5 min, skipped while `document.hidden`, catch-up on `visibilitychange` when stale, one in flight at a time), "Refresh now" button (marked `aria-disabled` while busy rather than `disabled`, which would drop its keyboard focus), the footer's "Updated HH:MM" (time of the last refresh that loaded `results.json`, not of the last attempt), minute ticker for relative ages, `hashchange`
- `data.js` — `fetchAll()` (relative paths; each file has a 30 s deadline covering the request and the body read, so a stalled request ends as unreachable instead of blocking every later refresh; a failed fetch returns `null` and the last good copy in `state` is kept — also for `announcement-state.json` and `run_state.json`, which only a real 404 or valid data clears, so one failed fetch never hides an incident banner or the run chip) and the shared `state` (cached data, `config`, `pinnedRunTs`, `historyLoaded`, `resultsLoadedMs`)
- `format.js` / `status.js` — pure helpers (escaping, timestamps with zone names, ages, `getRunStatus`, `knownStatus` whitelists, `RUN_TIMESTAMP_RE`, `parseRunHash`, `runOverdue`/`healthStale`, `cleanupBadge`, the service catalog)
- `dom.js` (activatable elements, roving tab stop with focus restore, tooltip anchoring: left-half cells anchor left, right-half cells right, with tooltips capped at half the viewport so none is clipped), `header.js`, `timeline.js`, `health.js`, `services.js`, `modal.js`, `charts.js`, `cleanup.js`, `announcements.js`, `theme.js` (custom logo/favicon probed with a `no-store` GET; a custom stylesheet `<link>` is removed when its `sheet` is still `null` after the window `load` event, by which time every stylesheet has loaded or failed — no re-download)

`serve.py` builds `DASHBOARD_MODULES` once at startup from `SERVE_ROOT/js/*.js` (the directory is root-owned and read-only at runtime; `test_every_dashboard_module_is_served` fetches each one), pins `.js` to `text/javascript`, and sends the modules **and `index.html`** `Cache-Control: no-cache` (ETag revalidation) because import specifiers carry no `?v=` cache-buster — a `max-age` could pair a new `main.js` with stale imports, or a cached page with newer modules, after a deploy. Other static assets keep `max-age=300`. The node tests import the modules directly (`dashboard/node_testlib.py`: an ESM runner plus a small fake DOM, and `extract_function`/`run_script` for the classic-script `report.js`, which runs `initReport()` at load; `dashboard/js/package.json` marks the directory as ESM for node and is not served); they are split by area into `test_dashboard_{header,timeline,cards,main}.py` plus `test_getrunstatus.py`.

Behavior worth knowing:
- **Run permalink** — a pinned historical run is identified by its timestamp (`state.pinnedRunTs`), never an array index, so pruning does not shift the pin. Selecting a run writes `#run=<ts>` with `history.replaceState`; the hash is read on first load and on `hashchange` and validated against `RUN_TIMESTAMP_RE` (an empty hash or a bare `#` returns to the latest run; any other invalid fragment is ignored); a valid timestamp no longer in `history.json` falls back to the latest run with a notice — but only once `history.json` has loaded successfully (`state.historyLoaded`), and for a `hashchange` to a timestamp missing from the cached history only after one fresh refresh (the run may have finished since the last one; main.js registers it via `setRefreshHook`). Until then the pin and the hash are kept and the live view shows.
- **Freshness** — the header shows the last run's and last health check's age (from the run's start; the line is hidden while `health.json` holds the first-boot placeholder `"waiting"`, which `format.js` treats like `waiting_for_first_run`); each turns amber with "(overdue)" under the exporter's rules, from `dashboard_config.json`: a run when `now - (start + run_duration_seconds) > 2 × schedule_interval_seconds + run_duration_seconds` (`runOverdue`, KEEP IN SYNC with `RallyStaleResults`), a health check past `health_stale_after_seconds` (`healthStale`, KEEP IN SYNC with `health_metrics.py::stale_after_seconds`). Without the config nothing is marked overdue. A failed `results.json` fetch shows the "Can't reach server / Can't load results.json, showing data from HH:MM" chip; a first-load failure shows "Data unavailable".
- **Run errors** — a summary with a top-level `.error` renders a full-width error card (error, `error_detail` as text, the `<RUN_DIR>/deployment.log` or `run.log` path) in the services grid.
- **Accessibility** — service cards are `role=button` with `tabindex=0` and Enter/Space; each timeline is one Tab stop (roving tabindex, arrow/Home/End) because it can hold hundreds of cells, kept on the pinned run, and a re-render (select, Back to Latest, refresh) puts focus back on the same run or check (cells carry `data-key` = timestamp), and a refresh that replaces the service cards puts focus back on the same service's card (`data-service`, else the services heading); tooltips are `aria-hidden` with the same text as the cell's aria-label and also show on focus; the modal is `role=dialog`/`aria-modal` with focus moved in (the overlay's `visibility` flips at once on open and is delayed only on close, since `focus()` on a still-hidden element is a no-op), trapped, Escape to close and focus returned to the opener (or, when a refresh replaced it, to the same service's card via `data-service`, else the services heading); `prefers-reduced-motion` disables the CSS animations and transitions, and `charts.js` passes Chart.js `animation: false` (CSS cannot reach canvas drawing); the card fade-in plays only on the first render.

### Theme Customization

Dashboard theming follows a narrow `themes/<name>/` contract without a build step. The shipped default theme is `/dashboard/themes/default/` and contains `tokens.css`, `logo.svg`, and `favicon.svg`. At container startup, `scripts/init_state.sh` (as rally) ensures `/results/branding/` exists and `scripts/entrypoint.sh` recreates `/dashboard/themes/custom -> /results/branding`.

`dashboard/index.html` loads styles in this cascade order: `themes/default/tokens.css`, `style.css` (base, header, timelines), `cards.css` (service cards, charts, cleanup), `overlays.css` (modal, banners, footer, responsive overrides, card animations), `themes/custom/tokens.css`, then `themes/custom/overrides.css`. The three dashboard stylesheets are one stylesheet split by section; keep their order. The full reports load only `style.css` (plus `report.css`). Custom files are optional and partial; missing custom assets fall back to defaults. `dashboard/js/theme.js` probes `themes/custom/logo.svg` and `themes/custom/favicon.svg` with GET at boot, then swaps the header logo and favicon only when those files exist.

`dashboard/serve.py` keeps a deny-by-default allowlist with four branches: `ALLOWED_STATIC` (own assets, including `report.css`/`report.js` and the `DASHBOARD_MODULES` set of `js/*.js` files), `ALLOWED_JSON_SYMLINKS` (JSON symlinks resolving into `/results/`), the theme branch, and the served-report branch. Theme paths must live under `themes/`, use one of `.css`, `.svg`, `.png`, or `.ico`, and resolve either under `/dashboard/themes/` or under the tighter `/results/branding/` custom-theme root. Do not widen this to all of `/results/`.

The fourth branch serves the per-run HTML reports: the regex `^runs/[0-9]{8}T[0-9]{6}Z/[a-z0-9_-]+\.html$` (anchored, no separators inside the captures) plus re-checked `RESULTS_ROOT` containment on the resolved target, reached via the `/dashboard/runs -> /results` symlink. **There is a single strict CSP for every response** (`SECURITY_HEADERS`: `script-src 'self'`, no `'unsafe-inline'` in `script-src`, no external origins, no `sandbox`). The reports earn the strict policy because they are now rendered by `scripts/render_report.py` (see Full Report) from same-origin assets only — no CDN, no inline executable script. The earlier per-path `REPORT_SECURITY_HEADERS` (relaxed `'unsafe-inline'` + `ajax.googleapis.com`/`cdnjs.cloudflare.com` + `sandbox`) and the per-instance header-swap/leak-reset logic were **removed** along with the rally-generated AngularJS report they existed to serve. `ALLOWED_JSON_SYMLINKS` includes `dashboard_config.json` (written at boot), `run_state.json` and `announcement-state.json`; the last two 404 until first written: the name passes the allowlist, then the dangling symlink fails the `target.is_file()` check, the same 404 as any missing or disallowed path.

`serve.py` resolves the request against the allowlist **before** checking existence, and every allowlist denial is the same `404` as a missing file, so status codes are no existence oracle (only a `..` path is a path-only `403`). `HEAD` is served like `GET` without a body (and without compressing: a gzip `HEAD` carries `Content-Length` only when the gzip body is already cached). Successful file responses (`200`, including `HEAD`) and `304`s carry `ETag` (mtime + size; the gzip body's tag gets a `-gz` suffix, and the gzip body is built with `mtime=0` so the same tag always means the same bytes) and `Last-Modified`; error responses carry neither; `If-None-Match` (preferred) / `If-Modified-Since` get a `304` that still carries `SECURITY_HEADERS`. HTML/JS/CSS/JSON/SVG are gzipped when `Accept-Encoding` gives gzip a nonzero q (an explicit `gzip` entry beats `*`) with `Vary: Accept-Encoding`; the last gzip body is cached by ETag (`_GZIP_CACHE`) for the `ALLOWED_STATIC` and `ALLOWED_JSON_SYMLINKS` names only (a fixed set, so the cache is bounded), so an unchanged file is not recompressed on every refresh; run reports and theme assets are compressed on the fly. JSON is `Cache-Control: no-cache` (always revalidate, reuse on 304), static assets `public, max-age=300`. The CSP also sets `base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `X-XSS-Protection` is `0`, and reading the request line and headers uses a per-recv `SOCKET_TIMEOUT_SECONDS` (30) so a silent or stalled client cannot pin a `ThreadingHTTPServer` thread (a client that drip-feeds bytes is **not** bounded: that is a known limit, covered by a reverse proxy in front); the response write then gets `RESPONSE_TIMEOUT_SECONDS` (600), because Python's `sendall` timeout caps the whole send and the short one would truncate large bodies on slow links.

### Full Report

The "Full Rally report" linked from each service card is a self-contained, dashboard-themed page generated by `scripts/render_report.py` (invoked from `run_tests.sh::run_service_tests`, replacing `rally task report`). For each service it reads the persisted `rally task results` JSON (`<RUN_DIR>/<service>.json`; the "old-json-results" shape: a list of workloads with `key.{name,description,kw}`, `result[].{duration,atomic_actions,error}`, `sla[]`, `hooks`, `load_duration`, `full_duration`), normalizes it into a small render-ready payload, and emits `<RUN_DIR>/<service>.html`. That HTML embeds the payload in a non-executable `<script type="application/json" id="rally-report-data">` block (exempt from `script-src`) and references the dashboard's own theme cascade plus `report.css`, `report.js`, and the vendored Chart.js — all by **relative** `../../` path so it works behind a sub-path reverse proxy. `report.css` and `report.js` carry `?v=<ASSET_VERSION>` (a constant in `render_report.py`, same date-plus-letter scheme as `index.html`'s `?v=`; bump it whenever either file changes; `serve.py` drops the query string before the allowlist check). `dashboard/report.js` renders it client-side: a working collapsible left nav (our own click handlers — the rally/AngularJS nav's `ng-show`/`ng-hide` broke when the CDN scripts did not load), an overview table whose rows open their scenario, and per-scenario detail (atomic-action duration bar chart, SLA table, error tracebacks, input config). Views are routed by the URL hash (`#overview`, `#input`, `#scenario=<idx>`), so they are linkable and back/forward work; with no hash the report opens on the first failed scenario (the overview when all passed). Nav items carry a visually-hidden pass/fail label and `aria-current`. The header shows the run time as readable UTC and the back link `../../index.html#run=<ts>` carries the run timestamp for the dashboard's run permalink (only for a real rally timestamp), so Back opens the dashboard pinned to that run. Rendering is best-effort: `render_report.py` degrades a malformed/empty/partial results file (including truthy-but-non-dict `key`/`kw`/`runner` shapes) to a valid empty-state report and exits 0, so the dashboard link never 404s. Because every asset is same-origin and there is zero inline executable script, the report needs no CDN, no relaxed CSP, and no `sandbox`, and renders with no network access (air-gapped friendly). A custom theme restyles reports for free via the same token cascade.

`scripts/backfill_reports.sh` heals reports from *before* this migration. A pre-upgrade run directory still holds the old `rally task report` AngularJS HTML, which renders broken (raw `{{...}}` placeholders) under the new strict CSP because its CDN scripts are blocked. `entrypoint.sh` backgrounds the backfill as the rally user on every boot (after the dashboard symlinks, before starting services): it walks every `<RUN_DIR>` and re-renders `<service>.html` from the persisted `<service>.json` via `render_report.py`, so deploying the new image fixes historical reports immediately instead of waiting out `RALLY_RESULTS_RETENTION_DAYS`. It is idempotent (skips any report already carrying the `id="rally-report-data"` data-block marker, so steady-state cost is one `grep` per report) and best-effort (a malformed/missing JSON yields a valid empty-state report). Its run-directory guard (`^[0-9]{8}T[0-9]{6}Z$`) and service-token guard (`^[a-z0-9_-]+$`) mirror `serve.py`'s `RUN_REPORT_RE` and `parse_rally_services` — **KEEP IN SYNC** — so it never descends into `branding/` or emits a non-servable report. It skips each run directory's `summary.json` and `task_args.json` (`run_tests.sh` bookkeeping that matches the service-token pattern but is not Rally results) and deletes the junk `summary.html`/`task_args.html` earlier backfills rendered from them, only when the matching `.json` is beside it and it carries the data-block marker. `entrypoint.sh` `%q`-quotes `RESULTS_DIR` into the `su -c` string so an operator-set value with shell metacharacters cannot break out.

Public theme tokens are documented in `docs/CUSTOMIZING.md`. Internal glass/radius/shadow tokens and decorative alpha literals are not stable API. SVGs loaded via `<img>` do not inherit page CSS variables, so a custom theme must supply its own `logo.svg` to recolor the brand mark.

### Announcement System

Operator-authored dashboard banners are managed by `scripts/announce.sh` — a bash + jq CLI invoked via `docker exec -u rally rally-monitor /scripts/announce.sh ...`. State lives at `/results/announcement-state.json` (top-level shape: `{"announcements": [...]}`), written atomically via `tmpfile + mv`. No HTTP write endpoint is introduced; authorization equals "you can `docker exec -u rally` on the host."

The state file lives directly under `/results/` rather than under `/results/branding/` to avoid a collision with the documented read-only theme bind-mount pattern (`./my-theme:/results/branding:ro` in `docs/CUSTOMIZING.md`), which would otherwise silently break every write.

`scripts/entrypoint.sh` creates `/dashboard/announcement-state.json -> /results/announcement-state.json` unconditionally at startup; the file appears lazily on the first `post`, and `serve.py`'s `target.is_file()` check (run after the allowlist) 404s the dangling symlink until then. The dashboard fetches via the same GET surface as other JSON files: one entry in `ALLOWED_JSON_SYMLINKS`.

The CLI supports five subcommands: `post`, `update`, `clear`, `list`, and `auto-clear-if-all-green`. The last is invoked from `scripts/run_tests.sh::main` after `build_summary` and before `publish_dashboard_files`; it removes every `incident`-type record when the post-run summary is unambiguously all-green. The predicate is `(.services | length) > 0 AND (.error // null) == null AND (.services | to_entries | all(.value.status == "passed"))`. The empty-services and `.error` guards are critical — a naive `all(...)` returns `true` on the `{"services": {}, "error": "deployment_setup_failed"}` shape and would silently erase the incident banner during the exact failure mode it exists to communicate.

Mutating subcommands wrap their read-modify-write cycle in `flock` on `/results/.announce.lock`. Without this, an operator `post` running between a cron-driven `auto-clear-if-all-green`'s read and write would be silently overwritten. `list` is unlocked so it never blocks on a stuck mutator.

The dashboard renders one banner above the 7-day timeline. Body text is rendered via `textContent` (no Markdown, no HTML); a `<details>` element exposes progress updates and other concurrent records. Each banner carries a visible bracketed type label (`[INCIDENT]` / `[MAINTENANCE]` / `[SCHEDULED]`) so color is not the sole signal — color tokens reused from the public theme contract: `--color-failure` (incident), `--color-warning` (maintenance), `--color-brand-secondary` (scheduled). Auto-refresh preserves `<details>` open state when the same primary announcement is still active.

`announcement_metrics.py::apply_announcement_metrics` reads the same `announcement-state.json` on every scrape and emits `rally_announcement_active{type}` (all three enum labels always present, 0 when none) plus unlabeled `rally_maintenance_mode` (1 iff any `maintenance` record is active). A missing state file yields zeros, not an exporter error. The active-ness predicate (`is_announcement_active`: unknown type → inactive, where the JS side checks own keys only (`Object.hasOwn`) so `toString`/`constructor` never count; future `effective_from` → inactive; past/now `expires_at` → inactive; unparseable bounds ignored) is **KEEP IN SYNC** with `dashboard/js/announcements.js::isAnnouncementActive` (one case table, `testdata/announcement_active_cases.json`, runs against both: `test_announcement_metrics.py` and `dashboard/test_dashboard_cards.py`); label cardinality is enum-only (`ANNOUNCEMENT_TYPES`, mirroring `TYPE_LABELS` in js/announcements.js and `VALID_TYPES_RE` in announce.sh), so body/id text never becomes a label. `rally_maintenance_mode` drives the commented-out, opt-in maintenance-inhibition variants of `RallyTestFailure`/`RallyServiceDown`/`RallySLABreach` in `prometheus/rally_alerts.yml` (`… unless on(job, instance) rally_maintenance_mode == 1`; the gauge carries only the scrape labels, so `on(job, instance)` matches it against each rule's labeled series without suppressing other monitor instances), so one `announce.sh post --type maintenance` can silence both the banner and those alerts.

### Uptime Tracking

The dashboard shows two uptime badges (in the timeline section headers), both computed over `UPTIME_WINDOW_DAYS` (default 30):

- **Smoke-test uptime** — `run_tests.sh::record_smoke_result` appends `{timestamp, status}` to `/results/smoke_history.json` after every run (including the deployment-failure path) and recomputes the embedded `uptime` object. A run is `passed` only under the same all-green predicate `announce.sh` uses (non-empty services, no `.error`, all passed) — the predicate is duplicated in both scripts with keep-in-sync cross-references. The ledger is pruned by timestamp, so uptime coverage is independent of `RALLY_RESULTS_RETENTION_DAYS`. `publish_dashboard_files` embeds `uptime` into `results.json`; `record_smoke_result` also syncs it directly into an existing `results.json`. The deployment-failure path now calls `publish_dashboard_files` right after `record_smoke_result`, so `results.json`/`history.json` reflect the failure instead of the last green run — this is correct because `dashboard/js/status.js::getRunStatus` treats a summary with a non-empty `.error` OR empty services as **failed** (it no longer renders "All Healthy"). The failed run therefore appears as a failed timeline cell with the error surfaced in the tooltip (`Error: <error>`). The standalone `record_smoke_result` sync is retained as belt-and-suspenders for direct invocations and any future early-exit path that exits before a publish.
- **API uptime** — `health_check.sh` applies `scripts/health_history_filter.jq` (via `jq -f`, so tests exercise the shipped filter) to append the check, cap stored history (`UPTIME_WINDOW_DAYS * 24 * 60 / HEALTH_CHECK_INTERVAL`, floored at 672 so the 7-day health timeline never shrinks), and embed `uptime` into `health_history.json`. The count cap bounds storage; the timestamp cutoff defines the uptime window — they are intentionally separate. Uptime measures **reachability, not speed**: the filter counts a check as up whenever `.overall != "down"`, so a `degraded` check (every service answered but at least one exceeded `HEALTH_LATENCY_WARN_MS`) does not depress availability. This is **KEEP IN SYNC** with `health_metrics.py::apply_health_metrics`, which likewise treats `degraded`/`up` as `rally_api_up == 1`. (The unlabeled `rally_api_overall_up` gauge is intentionally stricter — it **fails closed**, mapping anything other than `up`/`degraded` to 0, including `unknown`/missing; see Prometheus Integration.)

`dashboard/js/health.js::renderUptimeBadge` hides a badge until its `uptime.percent` is a number, so first boots and pre-feature data files render unchanged. The latency chart plots at most `HEALTH_CHART_MAX_POINTS` (672) checks regardless of stored history size. Uptime is dashboard-only by design — Prometheus users can derive it with `avg_over_time()` on existing gauges.

### Orphan Detection

`scripts/cleanup_monitor.sh` runs after each Rally test suite. It queries each OpenStack service for resources prefixed with `s_rally_` (scenario resources) or `c_rally_` (context resources — projects, users, networks created by Rally contexts) and writes counts to `cleanup_metrics.json`. When `RGW_ADMIN_URL`, `RGW_ACCESS_KEY`, and `RGW_SECRET_KEY` are configured, it also queries the RGW admin REST API for orphaned implicit-tenant users and marks the scan as `ok`, `skipped`, or `error`. A failed or unparseable OpenStack list call is counted in `openstack_scan_errors` (status `error`, script exits 1) rather than read as zero orphans, and a resource with a null `Name` is treated as unnamed (`(.Name // "")`) instead of zeroing its type. **Every** resource type is scanned whatever `RALLY_SERVICES` says — one service's scenarios leave orphans in another's (nova contexts create `c_rally_*` networks/routers/security groups). A list call that fails with a missing-catalog-endpoint error is "not applicable" (skipped) only for a service **outside** the normalized `RALLY_SERVICES` set; for a monitored service it usually means a wrong `OS_INTERFACE`/`OS_REGION_NAME` and counts as a scan error (`os_service_monitored`, keystone always monitored). The same rule applies to `purge_orphans.sh` listings. The list → validate → filter path (`os_list_rally_resources`, one `jq` per listing), `parse_rally_services`, `RALLY_RUN_LOCK_FILE`, and the single `cleanup_metrics.json` seed (`seed_cleanup_metrics`, used by both `init_state.sh` and `run_lib.sh`) live in `scripts/os_helpers.sh`, shared by `cleanup_monitor.sh`, `purge_orphans.sh`, and `run_tests.sh`. The exporter exposes these as OpenStack cleanup gauges, `rally_cleanup_scan_ok` (drives `RallyCleanupScanDegraded`), plus `rally_rgw_*` metrics; the dashboard cleanup badge shows `SCAN ERROR` on a blind scan.

Provenance: `run_tests.sh::run_service_tests` brackets each `rally task start` with `scripts/rally_project_tracker.py` — one process and one openstacksdk session per task. It snapshots pre-existing `c_rally_*` projects (the shell waits — bounded at 120 s, with `read -t` on a FIFO the tracker writes, not a forking poll loop — so the snapshot never races the task), polls every 5 s (not longer: short-lived contexts would be missed), and takes a final poll on SIGTERM after the task exits, appending `<ts> <project_id> <service>` for each new ID. The ledger authorizes purge-data deletes, so the tracker fails closed: the snapshot is retried 3 times and, if it still fails, **nothing** is recorded for that task (an empty seen-set would attribute other runs' leftover projects to it); its project listing comes from `keystone_projects.list_projects(conn, "c_rally_")`, which uses Keystone's server-side inexact filter `name__startswith` (supported: `keystone/api/projects.py` passes `name` to `build_driver_hints`, which accepts `<attr>__startswith`) so only Rally context projects count against `list_limit`, and still raises on a truncated response. Only IDs matching `^[A-Za-z0-9_-]+$` are recorded. The SIGTERM handler only sets a flag (an `Event.set()` from a handler can deadlock) and the loop sleeps in 0.2 s slices. It exits if its parent shell dies; `stop_project_tracker` SIGKILLs it if it has not exited 60 s after SIGTERM, and a tracker that dies before signalling ready is logged with its exit code (its stderr goes to the run log). `TRACKER_PID` is cleared as soon as the tracker is known to have exited and `_tracker_running` checks bash's own job table (`jobs -rp`), never `kill -0`, so a recycled PID is never signalled.

After the summary is built, `run_tests.sh` automatically purges rally-owned RGW orphans via `auto_purge_rgw()`, then refreshes `cleanup_metrics.json` so dashboard and Prometheus state reflect the post-purge state. This only runs when RGW admin credentials are configured. It is fail-closed: if the orphan scan had errors or Keystone lookups were inconclusive, purge is skipped entirely. Only users whose project IDs appear in `rally_project_ids.log` are eligible for deletion. Unknown-owner orphans are never touched by the automatic purge. For non-RGW resources, `purge_orphans.sh` remains the manual cleanup tool. `purge_orphans.sh --confirm` takes the same run lock `run_tests.sh` holds for its whole lifetime — one setting, `RALLY_RUN_LOCK_FILE` (default `/rally/logs/rally-run.lock`) in `os_helpers.sh`, sourced by both and by `init_state.sh`, which creates the file at boot as rally (replacing a copy rally cannot write, e.g. one a root run of an older image left behind). `--confirm` refuses with exit 4 when it cannot actually hold the lock: a run holds it, the file is missing (proceeding unlocked would let a cron run create and take it mid-purge), or it cannot be opened. It opens the lock **read-only** and never creates it (and a root invocation re-executes as rally first, see Container Privilege Model). Trade-off: a scheduled run that fires during a purge skips itself, and `run_tests.sh` logs a `SKIPPED: … held by another test run or by purge_orphans.sh --confirm` line. A dry run never touches the lock (even a brief exclusive probe could make a starting cron run skip); it warns when `run_state.json` says `running`. In Phase 2 each RGW user's buckets are re-inventoried immediately before its delete from the **stats-free** listing `rgw_list_user_bucket_names` (`GET /admin/bucket?uid=` without `stats`; with `stats=true`, Reef/Quincy silently omit buckets whose stats failed). A fresh stats listing must name the same buckets or the user is skipped (fail closed). The inventory drives the deleted/failed counts and the audit log's `rgw_buckets_purged`; buckets created since Phase 1 count against `MAX_DELETE_THRESHOLD`; an empty unknown-owner user that gained a bucket is skipped; a 404 (already absent) counts as zero deletions. After a **failed** purge-data request the user and its buckets are re-checked: user gone → counted as deleted; buckets partly gone → the removed ones are recorded as purged and the rest as failed. After a client-side **timeout** (curl exit 28; `rgw_delete_user` returns 3) RGW may still be deleting, and a stable bucket list proves nothing (objects inside may still be deleting), so the only definitive outcome is the user being gone (authoritative 404): the re-check repeats with backoff through the whole budget (`RGW_SETTLE_DELAYS`, default 10+20+40+80+150 s) and, unless the user disappears (counted as deleted with all its buckets) or a look fails, the user is INDETERMINATE: counted in `total_indeterminate` and listed in `rgw_users_indeterminate` in the audit log, neither deleted nor failed, and the script exits 1. The RGW phases live in `scripts/purge_rgw.sh` (sourced by `purge_orphans.sh`). Exit codes: 1 invalid config/usage or a deletion failed / RGW purge skipped, 2 threshold, 3 a Phase 1 list call failed (dry run too), 4 run in progress.

The **manual** `purge_orphans.sh` applies a slightly broader RGW policy than `auto_purge_rgw()`: beyond rally-owned orphans, it also reaps **empty unknown-owner** orphans — users whose Keystone project is *confirmed gone* (`rgw_find_orphaned_users` only emits authoritative 404s; inconclusive lookups raise `_RGW_LISTING_ERRORS` and abort the purge) **and** which hold **zero buckets/objects**. Zero data means zero loss, and Keystone implicit-tenant users self-heal (Ceph recreates them on the next authenticated access), so an empty dangling user is always safe to delete. This clears pre-provenance-ledger orphans — RGW users from projects deleted before `rally_project_ids.log` logging began — that the ledger gate alone leaves stuck as `unknown_owner` forever (making `RallyRgwOrphanedUsers` fire indefinitely). Unknown-owner orphans that still hold **data** are always skipped — they need a human. The empty-orphan count is recorded as `rgw_empty_unknown_owner` in the purge audit log. `auto_purge_rgw()` is deliberately unchanged and never applies this broader policy.

Trust assumptions behind the orphan logic (not enforced in code — Keystone exposes no reliable, policy-independent way to tell a cloud-admin token from a domain-scoped one): (1) the monitor's credentials see **every** project in **every** domain (cloud-admin / system scope), because the RGW anti-join treats "absent from the project list" as "deleted" — a narrower scope would make other domains' live projects look gone; (2) `c_rally_*` / `s_rally_*` names are created only by this monitor, because name prefix (plus the provenance ledger for RGW) is what authorizes deletion. Input validation fails closed instead of trusting partial data, and every allowlist regex on the ledger/deletion path anchors to the whole string — Python uses `fullmatch()` and jq uses `\A…\z`, because in both `$` also matches before a trailing newline (an ID like `"victim\n"` would otherwise print as two lines and could vouch for another project); the tracker additionally refuses to write a ledger line whose ID or service is not a fullmatch of its charset. Beyond that: one **structurally** malformed record (non-object, missing/non-string/empty `id`, non-string `name`) rejects the whole Keystone project listing (`keystone_projects.py`); an unusual-but-valid string ID is kept in the listing but printed/recorded only if it matches `^[A-Za-z0-9_-]+$`, a superset of the implicit-tenant uid charset `[A-Za-z0-9-]` (**KEEP IN SYNC** with `rgw_implicit_project_id` / `_rgw_implicit_pairs`), so omitting it can never invent an orphan, and one `s_rally_*`/`c_rally_*` OpenStack entry without a valid `^[A-Za-z0-9_-]+$` ID rejects that whole resource listing (`os_helpers.sh::_os_rally_rows`).

`rally_project_ids.log` is the **sole authorization basis** for RGW auto-purge, so `run_tests.sh` prunes it on its own `PROVENANCE_RETENTION_DAYS` window (default 90), deliberately decoupled from `RALLY_RESULTS_RETENTION_DAYS` (default 7) — the same defect class as the `smoke_history.json` retention decoupling. Pruning the ledger on the short run-retention window would degrade older orphans to unknown-owner (never purged), making `RallyRgwOrphanedUsers` fire forever.

### Rally Scenarios

Located in `rally/scenarios/`. The monitored service set is configurable via `RALLY_SERVICES` (default `keystone,nova,neutron,glance,cinder,swift`), which drives `run_tests.sh`, `api_health_check.py`, and the boot-time seed in `init_state.sh` (pending cards generated from the set by calling `os_helpers.sh::parse_rally_services`). The normalization is **identical across three parsers** — split on commas, trim/strip whitespace, lowercase, drop empty segments, dedupe preserving first-seen order, then drop any token not matching the `^[a-z0-9_-]+$` allowlist — documented as **KEEP IN SYNC** between `os_helpers.sh::parse_rally_services` (sourced by `run_tests.sh`), `api_health_check.py::parse_rally_services`, and `scripts/health_fallback_filter.jq` (the all-down health document `health_check.sh` publishes when the checker fails); `scripts/test_parse_rally_services.py` runs one case table against all three. The allowlist is **path-traversal hardening**: service names index `rally/scenarios/<name>.yaml` and `runs/<ts>/<name>.html`, so a token like `../etc` must never survive. When every configured token is dropped (all invalid, or unset/empty), all three fall back to the default set. Unknown but valid names are tolerated: a smoke run logs `SKIP` for a service with no `rally/scenarios/<name>.yaml`; the health check logs a warning and omits a name with no registered checker (dropped invalid tokens are warned to stderr). `keystone` is always health-checked regardless (the openstacksdk session authenticates against it, so its token issuance *is* a keystone availability check; new scenario packs like octavia/heat/designate were deliberately deferred pending real-cloud validation). Scenarios are parameterized via `--task-args-file` with `RALLY_NOVA_FLAVOR`, `RALLY_NOVA_IMAGE`, and `OS_AUTH_URL` from the environment.

### Cron Environment

Environment variables are exported to `/rally/rally_env` (mode 0640) at container startup and sourced by cron jobs. The file contains `OS_PASSWORD` and (when configured) `RGW_SECRET_KEY` — do not loosen its permissions.

Startup validation (`entrypoint_config.sh`, before any side effect): `check_os_credentials` exits when `OS_AUTH_URL`/`OS_USERNAME`/`OS_PASSWORD`/`OS_PROJECT_NAME` is empty (names only, never values) and warns on the `env.sample` placeholders; intervals, timeout and ports are normalized and a malformed one stops the container. The three day counts (`normalize_days` 1.., `normalize_retention_days` 0.., `normalize_provenance_days` 1.. with a ledger-specific warning for 0; all capped at 36500 via `_clamp_days`) are **never fatal** — values that ran before validation existed must not crash-loop: out-of-range values are clamped and a non-number falls back to the default through `or_default`, each with a WARNING. `health_check.sh` and `run_tests.sh` re-validate through `or_default` (fall back to the default with a warning) because cron/`docker exec` can start them without the entrypoint — a bad `UPTIME_WINDOW_DAYS` used to abort `health_check.sh` after `health.json` was written, freezing the history.

### Container Privilege Model

Compose drops every capability except `SETUID`/`SETGID` and sets `no-new-privileges:true`, so root inside the container has no `DAC_OVERRIDE`/`CHOWN`/`FOWNER` and can write only where it owns the directory. The Dockerfile keeps code and config root-owned and not group/world-writable (`/scripts`, `/exporter`, `/dashboard`, `/rally`, `/rally/config`): root runs `entrypoint.sh` and sources `entrypoint_config.sh`/`os_helpers.sh` on every start, so a rally-writable `/scripts` would be a rally→root escalation on restart. Only `/results`, `/rally/data`, `/rally/logs` (rally:root 0770) and rally's home `/home/rally` (holds the ephemeral `~/.rally/globals`; `/rally` used to be the home) are rally-writable. Bytecode is precompiled at build (`compileall`) because the runtime user cannot write `__pycache__`.

**Root never writes into a rally-writable directory**: a symlink rally planted there would redirect root's truncate/chmod onto an arbitrary file. So `entrypoint.sh` does only root-only work (`/rally/rally_env` in the root-owned `/rally`, `/etc/cron.d`, the `/dashboard` symlinks — all `ln -sfnT`, so a destination that is already a symlink to a directory is never followed into the rally-writable `/results` — `rally db recreate` via `su`; even the needs-first-run check reads `latest_summary.json` via `su rally`) and runs `scripts/init_state.sh` **as rally** for everything under `/results` and `/rally/logs`: the lock files (run, health, cleanup, announce — one it cannot write is replaced; nothing holds a lock yet at that point), repair of root-run leftovers (an unwritable top-level `/results` file is replaced by a rally-owned copy via copy + mv; an unwritable `<TS>/` run directory cannot be fixed without `CAP_CHOWN`, so it is logged with the host-side `busybox chown -R 1500:0` fix, and `run_lib.sh::prune_old_results` checks each expired directory for unwritable subdirectories **before** deleting and skips it whole with a WARNING — a partial `rm -rf` would bump its mtime out of the `-mtime` window and silence the warning forever), the first-boot JSON seeds, the idle `run_state.json` reset, and `dashboard_config.json` (each published with `publish_json <name> <producer...>`: the producer's output goes to a `.tmp` that is moved over the target only when the producer succeeded and wrote something — a failed producer keeps the previous file, or leaves a seed missing so the next boot retries, with a WARNING and without stopping the container — after removing any directory or symlink rally left on the name, since `mv` onto one would drop the file inside it). The cron log files are created (`touch`) and tailed by the `tail -F` forwarder running as rally, and `docker/logrotate.conf` rotates as rally (`su rally root`). Lock paths live in `os_helpers.sh`: `RALLY_RUN_LOCK_FILE` (exported to cron via `rally_env`), `HEALTH_LOCKFILE` and `CLEANUP_LOCK_FILE` (env overrides are **test-only**, not user config — they are not in `RALLY_ENV_VARS`, so a container-level override would reach `init_state.sh` but not cron), and `ANNOUNCE_LOCK_FILE` (derived from `RESULTS_DIR`, shared by `announce.sh` and `init_state.sh`).

`os_helpers.sh::reexec_as_rally` makes every shell entry script (all of `scripts/*.sh` except `entrypoint.sh` and the source-only libraries; enforced by `scripts/test_reexec_guard.py`) re-execute itself as rally (`su` without `--login`, so the environment and cwd carry over) when started as root, so a `docker exec` without `-u rally` cannot create root-owned locks/state that make later cron runs fail silently. It is a no-op for non-root users and where no `rally` account exists (local dev, CI).

Secrets never go into a process's argv (world-readable via `/proc/<pid>/cmdline`): `notify.sh` passes `NOTIFY_WEBHOOK_URL` and `rgw_helpers.sh::rgw_curl` passes `RGW_ACCESS_KEY:RGW_SECRET_KEY` to curl through `-K <(printf ...)` config on a file descriptor, escaped by the single `os_helpers.sh::curl_config_quote` (`rgw_helpers.sh` sources `os_helpers.sh` itself so it works stand-alone). The test shims read that `-K` file to assert on it.

`.dockerignore` keeps `.git`, tooling directories, docs and test-only files (`test_*.py`, `conftest.py`, `exporter/exporter_testlib.py`, `scripts/shell_testlib.py` (shared `BASH`/`BASE_PATH` and shim writers), the shared case tables in `testdata/`, `dashboard/node_testlib.py`, `requirements-test.txt`) out of the image; nothing at runtime imports them, and CI runs pytest from the repository.

### patch_rally.py

`scripts/patch_rally.py` is applied at Docker build time to patch Rally's internal password-generation policy. It runs once inside the image build (via `RUN python3 /scripts/patch_rally.py` in the Dockerfile) and does not need to be re-run manually.

### RGW Helpers

`scripts/rgw_helpers.sh` is a source-only bash library used by `cleanup_monitor.sh`, `purge_orphans.sh`, and `run_tests.sh` (it holds `auto_purge_rgw`). It wraps the RGW admin REST API via `curl --aws-sigv4` (no Ceph CLI needed; the key pair reaches curl via a `-K` fd, never argv). Key functions: `rgw_list_implicit_users` (paginated user listing), `rgw_find_orphaned_users` (cross-references RGW against Keystone: one `awk` anti-join over the bulk project list; an empty or failed bulk list falls back to fail-closed per-project lookups), `rgw_classify_owner` (checks Rally provenance ledger), `rgw_delete_user uid [true]` (one `DELETE /admin/user`; `true` adds `purge-data=true` so RGW removes the user's buckets from its own tenant-correct listing, under the longer `RGW_PURGE_TIMEOUT`; returns 0 deleted, 2 already absent (404, logged, never counted as a deletion), 3 client-side timeout (curl 28; `purge_orphans.sh` then re-checks with `RGW_SETTLE_DELAYS` backoff), 1 failure). The bulk Keystone project list comes from `scripts/keystone_projects.py` (raw `GET /v3/projects` via openstacksdk), which exits nonzero when Keystone's `list_limit` truncated the response — `openstack project list` hides that flag, and a partial list would make live projects look deleted. The fallback then checks each distinct project ID over one SDK session (`keystone_projects.py --check`, IDs on stdin, `<id> exists|gone|error` out); `--check` first verifies the token's own `current_project_id` exists so an auth/endpoint 404 (or non-project-scoped token) fails closed with exit 1 and no stdout, after which only an explicit `gone` (HTTP 404) makes an orphan, and an `error` or missing answer is counted in `RGW_LAST_FIND_ERRORS` (fail closed). The uid→project-ID extraction is one awk pass (`_rgw_implicit_pairs`), the single definition of an implicit-tenant uid, shared by the anti-join, the fallback and `rgw_implicit_project_id`. There is deliberately **no per-bucket delete**: before Ceph Squid (19) `RGWOp_Bucket_Remove` ignores any tenant and resolves names in the global tenant, so a bare-name delete of an implicit-tenant bucket could hit another user's same-named bucket. Rally-owned users are deleted with purge-data; `purge_orphans.sh`'s empty unknown-owner users are deleted without it, so RGW refuses if a bucket appeared after Phase 1. `auto_purge_rgw()` gates all deletion on Rally ownership — only project IDs recorded in `rally_project_ids.log` are eligible. The manual `purge_orphans.sh` additionally reaps empty unknown-owner orphans (confirmed-gone project + zero buckets/objects); see Orphan Detection.

### Webhook Notifications

`scripts/notify.sh` fires an outbound webhook on smoke-status **transitions only**, invoked from `run_tests.sh::main` right after `record_smoke_result` on **both** the normal and `deployment_setup_failed` early-exit paths (always `|| true`, so a notification failure never affects the run). It is intentionally **predicate-free**: the caller hands it the status it already computed via the `RUN_SMOKE_STATUS` global, so the all-green predicate is *not* re-derived a third time (it lives in `run_tests.sh::record_smoke_result` and `announce.sh`'s `ALL_GREEN_PREDICATE`). notify.sh only compares the given status against `${RESULTS_DIR}/.last_notified_status` and sends on a change.

Behavior: off (silent no-op) unless `NOTIFY_WEBHOOK_URL` is set; a missing state file baselines to `passed` (first-ever failed run notifies, first-ever green run stays quiet); the state file is updated atomically (`tmp + mv`) **only on a successful send** (`curl --fail` exit 0), so a failed POST leaves the baseline intact and the next run retries. `NOTIFY_FORMAT` picks `generic`/`slack`/`discord` payload shapes; `NOTIFY_DASHBOARD_URL` is optionally embedded. `NOTIFY_WEBHOOK_URL` may embed a token, lands in `/rally/rally_env` (0640) alongside `OS_PASSWORD`, and is **never** echoed into logs or placed in curl's argv (passed via `-K` on a file descriptor).

### Prometheus Integration

- Scrape target: `<host>:9101/metrics`
- API health gauges (from `health.json`): `rally_api_up{service}` (degraded counts as up — reachability, not speed; clear-before-set each scrape, so a service dropping out of a snapshot leaves no stale series and a corrupt/missing file leaves NO per-service series), `rally_api_latency_milliseconds{service}` (where degraded slowness is visible), and unlabeled `rally_api_overall_up` which **fails closed**: `up`/`degraded` → 1, everything else → 0 (explicit `down`, `unknown`/missing overall, corrupt/missing file, any unrecognized value). Because per-service series vanish when the pipeline breaks, this unlabeled gauge is the only one that can still signal a blind exporter — hence it must not retain a stale `1`. Staleness is re-evaluated on every scrape (an unchanged file ages): a `health.json` whose `timestamp` is older than `health_metrics.py::HEALTH_STALE_AFTER_SECONDS` or unparseable drops the per-service series and sets the overall gauge to 0. The threshold is three health-check intervals, floored at one interval + `HEALTH_CHECK_TIMEOUT` + 60s so one slow check never reads as stale; it is exported as `rally_api_stale_after_seconds`. `HEALTH_CHECK_TIMEOUT` (default 300 s) has one source: `entrypoint.sh` normalizes it (`normalize_timeout`, 1..3600) and exports it to the exporter and, via `rally_env`, to `health_check.sh` (the kill deadline); the scripts' own 300 fallbacks only cover a run without the entrypoint. `rally_api_last_check_timestamp` keeps the last parseable check time while `health.json` is missing or corrupt (0 only until a first check is seen), so `RallyApiHealthStale`, which ignores 0, still fires for a pipeline that breaks after working; after an exporter restart onto a broken file, `RallyApiSignalLost` is the remaining signal. `rally_api_last_check_timestamp` exports the check time
- Threshold gauges (set once at import): `rally_schedule_interval_seconds` is the longest gap cron leaves for `RALLY_SCHEDULE_INTERVAL`, and the health interval feeding `rally_api_stale_after_seconds` is the same for `HEALTH_CHECK_INTERVAL` (`metrics_common.py::cron_spacing_seconds`, **KEEP IN SYNC** with `entrypoint_config.sh::make_cron_schedule`'s whole-hour round-up and its shell twin `entrypoint_config.sh::cron_spacing_seconds`, which `init_state.sh` writes into `dashboard_config.json`). The exporter reads both env vars directly (inherited through `su`); `entrypoint.sh` refuses to start on an invalid value, so the exporter's default fallback only covers unset vars
- Run gauges: a summary with a top-level `.error` (`deployment_setup_failed`, `task_args_write_failed`) is valid data about a failed run — per-service series cleared, `rally_overall_success` 0, `rally_run_setup_ok` 0, `rally_run_duration_seconds` 0, `rally_last_run_timestamp` advanced. `rally_run_setup_ok` keeps its last value while the summary is unreadable (only meaningful with `rally_data_valid == 1`; its alert is gated on that). `rally_last_run_end_timestamp` = start + `run_duration_seconds` (just the start while the duration is not yet written or for an aborted run). A service whose task never started is `status: "failed"` with `error: "task_failed_to_start"`, so it clears `rally_overall_success` like any failure; the dashboard modal and its empty-state report show the reason
- Cleanup scan health (from `cleanup_metrics.json`): `rally_rgw_scan_ok` and `rally_cleanup_scan_ok` (0 when any OpenStack orphan listing failed, and 0 when `cleanup_metrics.json` is missing or corrupt — `init_state.sh` seeds it at boot, so that means a broken pipeline; a successfully parsed legacy file without `openstack_scan_status` reads as ok) — alerts `RallyRgwScanDegraded` / `RallyCleanupScanDegraded`
- Announcement gauges (from `announcement-state.json`): `rally_announcement_active{type}` (all three enum labels always emitted) and `rally_maintenance_mode`
- Alert rules: copy `prometheus/rally_alerts.yml` to your Prometheus rules directory and add it under `rule_files:` in `prometheus.yml`. The `rally_api` group adds `RallyApiDown` (critical, `rally_api_up == 0`, `for: 20m`) and `RallyApiSignalLost` (warning, `rally_api_overall_up == 0`, `for: 60m` — covers both a sustained overall outage and a broken/stale health pipeline whose absent per-service series cannot fire `RallyApiDown`) plus the narrower `RallyApiHealthStale` (warning, check older than `rally_api_stale_after_seconds`, `for: 15m`, ignores a 0 timestamp). `RallyStaleResults` measures from `rally_last_run_end_timestamp` and fires past `2 * rally_schedule_interval_seconds + rally_run_duration_seconds` (the next run finishes within one interval plus its own duration, even when cron ticks are skipped under the run flock); `RallyRunSetupFailed` (critical, `rally_run_setup_ok == 0`) owns aborted runs and `RallyOverallFailure` excludes them via a plain `unless rally_run_setup_ok == 0` (same labels, so per instance). **Label matching:** the labeled rules guard with `and on(job, instance) rally_data_valid == 1` — a bare `and` compares all labels and never matches `service`/`scenario` series (this silently disabled `RallyTestFailure`/`RallyServiceDown`/`RallySLABreach` before). Every alert has a `runbook` annotation (the four test-result alerts share one through a YAML anchor); purge runbooks dry-run first and use `-u rally`. `RallyTestFailure`/`RallyServiceDown`/`RallySLABreach` carry commented opt-in `unless on(job, instance) rally_maintenance_mode == 1` inhibition variants. `prometheus/rally_alerts_test.yml` holds promtool unit tests (assert on `ALERTS`, every series carries job/instance); `exporter/test_alert_rules.py` runs them when `promtool` is on PATH; locally it skips without promtool, but CI installs a pinned, checksum-verified promtool and, with `CI` set to anything but empty/`0`/`false`, a missing promtool fails the tests instead of skipping them (see CI)
- Uptime is dashboard-only by design; derive it Prometheus-side with `avg_over_time(rally_api_up[30d])`

### CI

`.github/workflows/build-push.yml` runs a `test` job with `shellcheck -x -P scripts scripts/*.sh` followed by `python -m pytest exporter/ dashboard/ scripts/` on Python 3.13 (matching the `python:3.13-slim` runtime; the script suites shell out to bash + jq, both on `ubuntu-latest`), and an `audit` job that installs pip-audit from the hashed lock `.github/ci/requirements-audit.txt` (generated from `requirements-audit.in`, installed with `--require-hashes`) and runs `pip-audit --disable-pip --require-hashes --strict` once per lock, `docker/requirements.txt` and that CI lock (separate invocations, because pip-audit rejects duplicate requirements once the shared packages' versions diverge) (no severity filter exists for PyPI advisories, so any known vulnerability fails it). The test job installs `exporter/requirements-test.txt` constrained (`-c`) by a hash-stripped copy of `docker/requirements.txt`, so the suites run against the image's transitive versions (hashes are stripped because pytest is not in that lock and any hash in a constraints file forces `--require-hashes`). A weekly `schedule:` trigger re-runs only the audit job (`test` and `build-push` are gated `if: github.event_name != 'schedule'`, so nothing is built or pushed), and only scheduled runs get their own concurrency group (`-schedule` suffix), so an audit never cancels a build while push and `workflow_dispatch` still share one group per ref and an older build cannot roll back `latest`. The `test` job installs a pinned, SHA-256-verified `promtool` (`PROMETHEUS_VERSION`/`PROMETHEUS_SHA256` in the job env, bumped by hand), and `exporter/test_alert_rules.py` fails rather than skips when `CI` is set and promtool is missing. The `build-push` job declares `needs: [test, audit]`, so a lint, test, or audit failure blocks the build. The build pushes the container image to GitHub Container Registry (`ghcr.io/<owner>/<repo>`) on push to `main`, on `v*` tags, on PRs to `main` (build-only, no push), and via manual dispatch. Auth uses the built-in `GITHUB_TOKEN` (`packages: write`), so no extra secrets are required. Every action is pinned to a full commit SHA with a `# vX.Y.Z` comment, and checkout runs with `persist-credentials: false`. The build context is the repo root with `docker/Dockerfile`, matching `docker/docker-compose.yml`. Tags are derived by `docker/metadata-action` (branch, PR ref, semver, SHA, and `latest` on the default branch); layer caching uses the GitHub Actions cache backend.

Dependencies are pinned to exact versions for reproducible images. The image's direct pins live only in `docker/requirements.in` (`flask`, `prometheus-client`, `gunicorn`, `rally-openstack==3.0.0`, `rally==5.0.1`, `python-openstackclient==10.1.0`, with the pinning rationale), and `docker/requirements.txt` is the pip-compile lockfile generated from it (every transitive package pinned and SHA-256-hashed, identical for amd64 and arm64); the Dockerfile installs **only** the lock, with `--require-hashes --only-binary=:all:` (no C toolchain in the image). The one exception is `murano-pkg-check`, whose only wheel is py2-only: it is built from its hashed sdist with `--no-binary=murano-pkg-check --no-build-isolation`, after `pbr` and `setuptools` are installed first from the same lock (extracted with `awk`), so its build backend is hash-checked too. After editing a direct pin, regenerate the lock with the command in `docker/requirements.in` (Linux, Python 3.13, `pip-tools==7.5.3` with `click==8.2.1`, because newer click makes that pip-tools write a bogus `--no-index` into the header); `exporter/test_requirements_lock.py` (parametrized over the image pair and the `.github/ci/requirements-audit.in`/`.txt` pair) fails when a pin in an `.in` file and its lock disagree, and when a lock has a non-hashed entry or a top-level option line. `exporter/requirements.txt` lists the exporter packages **unpinned** with `-c ../docker/requirements.txt`, so local dev (`cd exporter && pip install -r requirements.txt`) gets exactly the image's versions; the hashed constraints put pip in `--require-hashes` mode. `exporter/requirements-test.txt` lists the same packages unpinned plus `pytest==…` (not `-r requirements.txt`, which would demand a hash for pytest); CI constrains it with a hash-stripped copy of the lock. The base image is pinned as `python:3.13-slim@sha256:<index digest>`. The OpenStack toolchain in particular **must** stay pinned because `patch_rally.py` targets Rally module internals and the scenario YAMLs reference plugin names upstream renames across releases — a silent bump could move the patched code or rename a plugin out from under a build. `rally` is held at 5.0.1 because 5.1 rewrites the CLI on typer and `run_tests.sh` drives and parses that CLI. `.github/dependabot.yml` opens weekly bump PRs, with a 14-day release cooldown on every ecosystem except docker (Dependabot raises no advisory-based security updates for images, so the base-image digest bump is how security rebuilds arrive and must not wait): pip for `/docker` (owns every image pin; Dependabot only re-runs pip-compile when the bumped requirement is declared in an `.in` file, which is why the pins live in `docker/requirements.in` rather than a plain requirements file — keep it that way; regeneration in the same PR is expected but not yet confirmed on GitHub, and the lock test fails any PR whose pins and lock disagree), pip for `/exporter` (limited to `pytest`), pip for `/.github/ci` (`pip-audit`), the docker base-image digest, and GitHub Actions SHAs. Each PR is gated by the test and audit jobs, so version drift is always a reviewed, tested change rather than a transparent rebuild. The vendored Chart.js/Inter pins in the Dockerfile and the CI promtool version are bumped by hand.

`docker/docker-compose.yml` defaults to this published image (`image: ${RALLY_MONITOR_IMAGE:-ghcr.io/ching-kuo/openstack-rally-monitor:latest}`) while retaining the `build:` block, so `docker compose pull` fetches upstream and `docker compose up --build` still builds locally under the same tag.

Running the suite locally (`python -m pytest exporter/ dashboard/ scripts/`) requires **bash >= 4 on `PATH`** — the script-suite tests resolve the interpreter via `shutil.which("bash")`, and bash 4 introduced `mapfile`, which the scripts use. macOS ships bash 3.2 at `/bin/bash`, so install a newer one (`brew install bash`) and ensure it precedes `/bin/bash` on `PATH`. Treat the current pytest output as the source of truth for the collected-test count.

## MCP Tools: code-review-graph

**IMPORTANT: This project has a knowledge graph. ALWAYS use the
code-review-graph MCP tools BEFORE using Grep/Glob/Read to explore
the codebase.** The graph is faster, cheaper (fewer tokens), and gives
you structural context (callers, dependents, test coverage) that file
scanning cannot.

### When to use graph tools FIRST

- **Exploring code**: `semantic_search_nodes` or `query_graph` instead of Grep

- **Code review**: `detect_changes` + `get_review_context` instead of reading entire files
- **Finding relationships**: `query_graph` with callers_of/callees_of/imports_of/tests_for
- **Architecture questions**: `get_architecture_overview` + `list_communities`

Fall back to Grep/Glob/Read **only** when the graph doesn't cover what you need.
